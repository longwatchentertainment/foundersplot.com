# My whole economy trusted the phone, so I moved it to the server

Weekly build log from a solo dev building a mobile business sim (React Native/Expo, Zustand, Supabase, RevenueCat, AdMob). 56 commits, roughly 17,400 insertions against 2,700 deletions across 243 files. This is the week I found out my entire economy was client authoritative and spent nearly all of it fixing that, then had a second reviewer catch two bugs in my own fix that would have broken the game for every real player at launch.

The finding, in one sentence: my cloud sync took the entire local game state, cash, coins, every inventory count, and upserted it into Postgres verbatim. Row level security correctly stopped anyone from touching someone else's row, but nothing stopped you from writing anything you wanted into your own. A rooted phone, a modified save file, or a proxy rewriting the outgoing request could set any balance to anything and have it become your real, permanent cloud save. I even had a server authoritative harvest function already sitting in the codebase, wired up to exactly one place, a debug screen button, and never called from the actual action players use. A proven pattern doing nothing.

The fix was a four phase migration: orchard actions, then processing, then market, then achievements, daily login, and cosmetics, plus a resync endpoint that overwrites local state with server truth after every cloud pull. Every economy action now requires live connectivity and calls a real edge function backed by a security definer RPC instead of writing local state and hoping. Existing players get their progress adopted in via migration rather than reset, but only up to a cutoff keyed on account creation time, because adoption is itself a bypass if you leave it open forever. A new account can forge a save before its first server touch and have it adopted straight into the wallet.

Then I had someone review the whole thing rather than trust my own read of my own fix, and that is the part I would tell anyone doing similar work to actually do. It found two issues that would have been silent launch day failures. First, the only code path that created a player's server side rows was gated behind a dev only debug button, so a release build would have 404ed on every economy function for every real player, forever, with no error a normal user would understand. Second, coins bought with real money were credited locally by the client after claiming a grant, but the wallet is now the only balance that matters, so purchased coins would show up, be unspendable, and vanish on the next sync. Neither showed up in my own testing, because my workflow always has that debug button available, and I had not run any of this on a device since the first phase shipped.

Two smaller things worth passing on. A poll that fired every 15 seconds per active player regardless of whether anything could have changed, which on a free tier quota runs out after roughly 2,000 player hours, now gated behind a local hint with a slower fallback so the server still decides everything. And a weather job that loaded every due player into one query capped at 1,000 rows, now a straight SQL port running inside Postgres with no cap and no per player round trip. Neither mattered yet at my player count. Both would have, at the player count I am trying to reach.

I also skipped JS obfuscation and certificate pinning on the client on purpose. Neither stops a determined attacker, both cost real upkeep, and the actual fix was making the server the only place that mattered, not the client harder to read.

Everything above is deployed and code complete but has not run on an actual phone yet, only checked against a new SQL test suite that applies every migration to a throwaway Postgres and asserts the economy invariants directly. That gap, code review confidence versus a real device, is exactly the gap that hid the two critical bugs, so closing it is the entire job for next week before I let a single stranger near this build.
