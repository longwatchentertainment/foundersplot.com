When not to reuse a mechanic just because it looks similar

August 21, 2026 · written for other developers

Weekly build log from a solo dev building a mobile business sim (React Native/Expo, Zustand). This week was almost entirely about scoping and building six interacting economic subsystems for one game feature, and the main lesson was about when NOT to reuse an existing mechanic just because it looks similar on the surface.

The feature is a farmers market. A few weeks ago I shipped an MVP version (weekly window, fixed price premium, a manual "sell 1" button) deliberately scoped way down from the full design doc. This week I built the rest of it back in: a market reputation system, a separate customer-loyalty system, a wholesale-buyer archetype, food blogger reviews, NPC competitor booths, live weather-driven demand, and a booth-tier capacity upgrade. Six files, roughly 21k lines of diff when you include the store slice and check files that had to change alongside them (a lot of that is test churn from touching a shared slice, not new logic).

The interesting decision was reputation vs. loyalty. The design doc uses "loyal customers" language for both a long-run quality reputation and a short-run "do you show up every week" mechanic, and it would have been easy to build one number and call it done. I kept them mechanically separate on purpose: reputation is a lifetime, monotonically-increasing quality signal (never decreases, rewards "have you always been good"), loyalty is a consecutive-weekend attendance streak that resets the moment you skip a weekend (rewards "are you reliably showing up right now"). Two real-world phenomena, two different failure modes, sharing the same flavor text in the doc. Collapsing them into one stat would have meant a single bad weekend could tank a number that's supposed to represent months of consistent quality, which felt wrong the moment I thought about actually playing it.

Also pulled forward something that had been explicitly deferred to post-launch: real weather-driven demand. The original lean scope cut this specifically to avoid an external API dependency and a location-permission/privacy surface. Instead of using device location, I hardcoded a single location (south central Kansas, the same region the existing weather-event system already uses) and call Open-Meteo, which needs no API key and no account. Zero new privacy surface, zero new consent dialog, same free-tier discipline as everything else in this stack. Confirmed the tradeoff with a direct question before building rather than assuming it was fine to reopen a closed scoping decision.

Found one real bug via the headless test suite rather than on-device: the reputation promotion/demotion check could fire both directions in the same call under certain state, which would have looked like a UI glitch to any actual player (rank flickering in one frame). Caught and fixed before it ever got near a device.

Honest state of things: none of this is committed yet, and none of it has touched a real phone. It's built against the design doc, typechecks clean, and passes the full headless check suite, but "passes my own tests" and "survives me actually tapping through it" have diverged before in this project, so I'm not calling it done until it does. That's the next session. If you're building something similar, my one takeaway this week: when a design doc uses one phrase for two different mechanics, stop and ask whether they're actually the same number before you build one.
