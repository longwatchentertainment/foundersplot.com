Buying coins charged players and granted nothing

September 18, 2026 · written for other developers

Weekly build log from a solo dev on a mobile business sim (React Native/Expo, Zustand, Supabase, RevenueCat, AdMob). About 33 commits, roughly 1,900 insertions against 400 deletions across 31 files. Last week was a pure UI pass. This week was monetization plumbing and analytics, and it turned up the most embarrassing bug I've shipped so far.

The bug: buying coins charged the user and granted nothing. buyCoins() resolved true on a successful purchase and never called earnCoins(). The purchase path had been written, typechecked, and reviewed, and the missing line was invisible in every one of those because a successful no-op looks exactly like a success. The only thing that caught it was building the server side validation and then actually watching the balance on a device.

That fix became the real work. The RevenueCat webhook Edge Function had existed since my throwaway pipeline validation but only logged events. It now grants. Design notes that mattered: idempotency keyed on RevenueCat's own event.id via a partial unique index, so a retried delivery can't double grant; only INITIAL_PURCHASE and NON_RENEWING_PURCHASE grant, everything else including REFUND still gets logged for manual reconciliation because I have no synced coin balance table to claw back from and I'd rather have a known gap than a broken automated clawback; coins per product id live in a table I can edit in Supabase Studio rather than in the function body; and the grant goes through the same pending_coin_grants mailbox the referral system already uses, so the client just polls after purchase with the existing manual claim button as a fallback. Verified on a real device: sandbox purchase produced the event row, the grant row, and the grant was already claimed by the time I looked.

Second piece, the one I'm happiest with technically. Every economy constant moved out of code and into a game_config singleton row so I can retune prices post launch from real spend data without shipping a build. The implementation is smaller than it sounds: the constants in economy.ts became exported lets that applyGameConfig() reassigns in place. Because a named ES import is a live binding, all 11 files already importing those values pick up the new numbers with zero consumer side changes. Offline fallback is two layers, code defaults and then an MMKV cached last known good config applied synchronously before any network round trip, so a cold start on a plane doesn't hand out launch day prices. Proved it by editing one cost in Studio and confirming the in app price changed after relaunch.

Then a guardrail audit with no code changes, which I'm counting as work anyway. Traced all 14 spendCoins() call sites and every earnCoins() site to confirm coins never convert to or from the cash balance in either direction, confirmed both progression gates are pure lifetime stat checks with no paid bypass, and confirmed all 5 timer skips price proportionally to remaining time. Found one flat cost coin spend and decided it was fine because it's a one time event response, not a timer skip. No violations. Writing "no violations found" after two hours of reading your own code is a strange feeling, but an unaudited guardrail is just a comment.

Analytics got the rest of the Tier 1 funnel instrumented plus a migration adding 5 dashboard views for funnel steps, drop off, session exit by harvest number, gate pacing, and per beat fired versus acted. I revoked those views from anon and authenticated so PostgREST can't serve my aggregate business metrics over the public API. Worth checking if you build dashboards in Postgres.

Honest status, because "committed" is not "works": server side validation and the config table both have real device proof. The hook card, the dual path guardrail, the multi ad pricing, and the new icon and splash are code complete and typechecked only. I'm listing them separately in my own notes for exactly that reason.

One more lesson, filed rather than acted on. I scoped adding a second crop and found my type system has AppleVariety, AppleGrade, AppleInventory as actual type names threaded through half the codebase. Normally a rename you defer. Except saves are stored as a JSONB blob shaped by those exact types, which means the rename is a free refactor today and a data migration against live player saves the moment I have any. Multi crop is correctly post launch, but that rename is moving in front of launch. If you're storing your store as a blob, your type names are a schema.

Next week is stripping debug affordances out of the tester build, which is the hard prerequisite for recruiting strangers.
