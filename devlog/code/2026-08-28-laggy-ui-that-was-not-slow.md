# Laggy UI that wasn't slow: state that never re-rendered

Weekly build log from a solo dev building a mobile business sim (React Native/Expo, Zustand). Last week was a big feature-building week; this week was the opposite, small, humbling, and entirely about what happens when you finally run last week's code on a real device.

The headline bug: two separate UI elements that looked "laggy" but weren't actually slow, they just weren't re-rendering when their underlying state changed. I'm using Zustand with selective subscriptions (`useGameStore((s) => s.someField)`), which is great for performance but has a sharp edge: if a component only calls a getter function like `getMarketStatus()` in its render body without also subscribing to the specific fields that getter reads, React has no idea it needs to re-render when those fields change. The component will still show fresh data eventually, but only as a side effect of some OTHER subscribed field changing and forcing a repaint. That's exactly what was happening. `fetchMarketWeather()` mutated weather fields nobody was subscribed to, so the weather text only updated once a sale changed something else you were subscribed to. Same root cause, second bug: `toggleMarketGradeExclusion()` mutated a field with zero subscribers, so the toggle buttons looked unresponsive until an unrelated render came along and dragged the update in with it. Fix was a one-line addition per bug, subscribe to the specific fields the getter depends on, but finding the actual cause instead of just re-rendering harder took a minute of staring at the selector list. Lesson I'm taking forward: when a getter function reads derived state, audit whether every field it touches has an explicit subscriber somewhere in the component, not just the fields the JSX directly displays.

Second bug was much dumber and much easier: the price breakdown recap (see below) used an emoji to show whether demand was trending up or down, and the up-trend arrow was hardcoded for both directions. A bad-demand day showed the same celebratory arrow as a good one. Classic copy-paste-and-forget-to-change-the-condition bug, caught only because I was actually looking at the screen instead of just the numbers underneath it. This is the strongest argument I have this week for on-device testing being non-negotiable even when your headless suite is green: nothing in a unit test cares which emoji renders.

The one real feature this week: a price transparency layer. The market resolves a whole day's inventory against reputation, loyalty, demand, weather, and blogger-review multipliers in one function call, and until now that returned a single dollar total with the six contributing multipliers thrown away. Added a `MarketPriceBreakdown` return type that carries all six factors through `sellAtMarket()` and up through `resolveMarketDay()`'s results, and the debug recap now prints only the factors that actually moved a given sale off baseline, so a boring day stays a one-line summary and an interesting day shows exactly why. Currently rendered through a plain native `Alert`, which is a real ceiling: no table layout, no expand/collapse, nothing visual. A proper recap screen and a pre-resolve preview using the same math are logged in NEXT.md as deliberate follow-ups, not forgotten scope.

Net effect of the week: zero new mechanics, three real bugs fixed, one transparency feature shipped, and a much better sense of which parts of last week's build actually hold up under a thumb instead of a test runner. If you're sitting on a pile of "typechecks clean, never tapped" code, my takeaway is the boring one: the bugs that actually embarrass you in front of players are rarely in your business logic, they're in the wiring between your state and your UI.
