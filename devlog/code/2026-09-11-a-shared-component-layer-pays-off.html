A UI polish pass, and why a shared component layer pays off

September 11, 2026 · written for other developers

Weekly build log from a solo dev building a mobile business sim (React Native/Expo, Zustand, Supabase). This week was a pure UI/UX polish pass, zero new game logic, and it's a decent case study in how a shared component layer pays off once you've built it.

The domain-by-domain visual rebuild that's been running for a couple weeks (Orchard, Market, Account) finished its last leg on Processing. The pattern that made it worth doing screen by screen instead of all at once: I built one generic component, an ArtAsset slot that renders a real image if a source is supplied and a labeled dashed placeholder if it isn't, and every other screen just plugs illustrated assets into that same slot as they arrive. Market needed almost no new art at all because it could reuse Processing's product images through a shared recipeArtSources.ts lookup instead of commissioning its own. That's the actual payoff of the shared-component approach: the second and third domain to get the treatment cost a fraction of what the first one did.

Processing's shed also got pulled out of its own detail screen into a new Facilities entry screen, a BuildingCard component that knows how to render a locked "coming soon" building as easily as an unlocked one, specifically so a second facility later is one more card, not a rework. Small thing, but it's the kind of interface decision that's cheap now and expensive to retrofit later.

The bigger technical piece was ripping out React Native's native Alert.alert() across the app in favor of an illustrated PanelSheet component, wood-and-gold trim, parchment texture, centered card. About 85 confirmation, choice, and destructive-action call sites across four domains route through one presentAlert() wrapper already, so the entire swap was a rendering-backend change behind that one function, zero call sites touched. That's the argument for the abstraction layer paying rent: a redesign that touches literally every screen in the app took one file.

Two honest bugs from this pass. First, a lightweight toast banner for non-blocking confirmations (batch started, apples sold) looked fine in code and rendered wildly oversized on an actual device, bleeding off both screen edges with text riding over the status bar. Root cause: the box was sized with width plus aspectRatio and no explicit height or overflow: hidden, which works until some other prop (a transform, an unbounded-height sibling) breaks Yoga's ability to infer the box's real bounds, and then nothing constrains it. Fixed by computing width and height explicitly once and clipping overflow, instead of trusting aspectRatio to fully pin the layout. Lesson I keep relearning: aspectRatio-only sizing without an explicit fallback dimension is a layout footgun, not just a convenience. Second, there's a device-reported black-screen crash tied to a presentAlert() call reached through the new toast path that I have not root-caused yet. Dropped one leftover Android-only Modal prop as a low-risk simplification while investigating, but I'm not claiming that's the fix, and I'm saying so here rather than pretending it's closed.

Smaller notes: the asset pack that shipped this week (badges, stat icons, panel chrome) needed two fix rounds because several "transparent" PNGs actually had a checkerboard baked into the pixel data instead of real alpha, a reminder to spot-check alpha channels on any exported asset pack before wiring it in, not just eyeball it in a preview.

Net effect: no new content this week, but every screen in the app now shares one visual language and one popup system, and the reused-art pattern means the next domain to need a redesign should be cheaper than this one was.
